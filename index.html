01 · 为什么需要

AI 改代码，最容易翻车的地方

AI 改代码出错，常常不是因为能力不够，而是上下文不对：读得太多，抓不住重点； 读得太少，又会漏掉团队的约定。WeFi 先判断这次要做什么，再只加载这个任务需要的流程、规则和业务知识。

1.1核心特性

  • 路由选 Skill，不全局加载

    每次会话只注入一张简短的路由卡。AI 按你的话判断这是哪类工作，例如加功能、修缺陷、看代码、审 PR，然后只加载对应的那个 Skill。其他 Skill 的内容不进入上下文。

  • 流程逐层展开

    Skill 只写主干步骤，细节放在参考文件中，走到哪一步才读哪一份。参考文件离 Skill 最多两层引用，由构建检查保证。例如加一个小功能，改代码前必读约 1.3 万字；走方案流程约 2 万字。

  • 按任务拼装上下文

    • 规则按文件匹配：要改哪些文件，就只加载匹配这些文件路径和技术栈的规则。改 .tsx 时加载 React 规则，改样式时不加载接口规则。
    • 项目知识按条件读：每份知识写明「什么时候读」，条件成立才读。
    • 业务知识先搜后读：从需求中取出专有名词，在 FSD 和接口文档中搜索，只读命中的章节，不读整份索引。大小写、驼峰和缩写写法不同，都能搜到。

  • 两档轨道

    小改直接做；涉及接口契约、全局架构或 3 个以上业务模块时，先写方案，评审通过后再开发。线上故障走 hotfix。

  • 门禁兜底

    每次改动都运行项目真实的类型检查、Lint、测试和构建命令，并按改动大小自动选择检查范围。

它不替代你已有的工具

它不生成代码，也不做 CI。只管三件事：AI 该读什么、做到哪一步得停下、 改完拿什么证明。门禁跑的还是你自己项目里的 npm run build、 tsc、eslint。

.wefi/harness/ 加进了 .gitignore，不提交。原因：它每天自己更新， 提交了就会跟远端打架，而且每个人本地都有完整的一份。

一次请求走完的步骤

拿 issue PDB-901 举例：文件模板页的空列表文案要改成 No file templates yet. Upload one to get started.

你与 AI 的对话
做一下 PDB-901 读 issue PDB-901，写快照 .wefi/state/issues/PDB-901.md。 轨道：quick。单页面文案改动，不触及接口。 新建分支 feat/PDB-901-file-template-empty-text。 装载规则：ui-text.md「空状态必须写明为什么空，并给出下一步操作」。 修改 src/views/system/fileTemplate/index.vue:336。 wefi gate：typecheck、lint 通过。 浏览器验证：空列表显示新文案，控制台没有新增错误。截图已保存。 已完成。待确认：页面没有 Upload 入口，新文案引导的操作在本页不可达。 提个 PR 提交 feat: guide users to upload when file template list is empty，页脚 Refs: PDB-901。 PR #42 已创建。 PDB-901 已评论 PR 链接和验证结论，状态从 New 改为 Pending Review。
  1. 理解请求wefi-feature

    读 issue，写快照。要改什么、不碰什么，先定下来。

  2. 选轨道quick / plan / hotfix

    单页文案，不碰接口，走 quick，直接改。

  3. 装载规则wefi rules

    按要改的文件挑规则，只读挑中的。

  4. 改代码quick

    一个文件，一行文案，就这样。

  5. 门禁wefi gate

    类型检查、Lint、相关测试。范围按改动自动定。

  6. 浏览器验证运行验证

    打开受影响的页面，走一遍场景，截图留着。

  7. 审查子 Agent

    quick 轨道只在 diff 超 300 行、或动了共享路径时才派。

  8. 交付wefi-ship

    提交、push、开 PR，把 issue 状态也改了。

什么时候该走 plan

碰到接口契约、动全局架构、跨 3 个以上业务模块，就得先写方案。方案评审完、接口对齐了， 再分阶段开发，每段做完派子 Agent 看一遍。你也可以直接说「走方案」或「直接改」， 不用自己判断。

04 · 核心概念

记住六个词

规则文件不少，但真正要记的就这六个。剩下的都是它们摊开之后的细节。

模式
请求的类型：feature、bugfix、ship、review、explain、discuss。决定加载哪个 Skill。
轨道
流程的做法：quick 直接改，plan 先写方案，hotfix 只修故障。只用于 feature 和 bugfix。
变更
一件事的记录目录 .wefi/changes/<id>/，含评估、方案、评审记录。
门禁
wefi gate 执行的检查：类型检查、Lint、测试、构建、调宽检测。
项目知识库
.wefi/ 中本项目自己的内容：规则、模块说明、验证手册。
业务知识
.wefi/domain/ 中从 FSD 和接口表生成的共用知识，几个仓库共用。

4.1项目知识库里的文件

路径内容
config.yaml技术栈、门禁命令、审查阈值、项目管理系统、worktree
rules/项目规则。和团队规则一起，由 wefi rules 按文件匹配
knowledge/架构说明和模块说明。README.md 是知识表：哪些改动读哪个文件
verify.md运行验证手册：启动、登录、功能地图、构造数据、已知的坑
lessons.md教训台账
specs/、changes/、decisions/、sources/规格；一件事从评估到完成的文档；设计决策；原始材料索引
state/本地状态：issue 快照、截图、开发服务器。不提交
domain/业务知识的本地 clone，见 domain.repo。不提交

你说一句话，它选哪条流程

路由分三层，一层兜不住有下一层。你随时可以用 /wefi 直接指定， 不用管它怎么判。

层谁在判看什么管不住的情况
1Claude Code、Codex 自己10 个 Skill 的 description语义相近时选错，比如「评审 PR」和「提 PR」
2模型读一张表router-card.md：请求 → Skill表里没写的问法
3Skill 第 0 步自己判routing.md：信号 → 模式，还能跑命令确认信号本身模糊

第 1 层是宿主原生的语义匹配，第 2 层是显式映射，第 3 层兜底。第 3 层能做前两层做不到的事， 比如分不清 #12 是 PR 还是 issue 时跑一次 gh pr view。

你说模式SkillAI 做什么

「状态管理用 Zustand 还是 Context」discusswefi-discuss2 到 3 个选项和推荐，不改代码

06 · 工作方式

十个 Skill，一条流水线

Skill 是 AI 的入口。每个 SKILL.md 就两件事：什么时候用它，用的时候按什么步骤走。 各管一段，接起来就是完整的开发流程。

阶段Skill作用
入口wefi/wefi 的参数、接着做、hotfix、状态、更新、检查、命令列表
理解wefi-explain现有代码怎么工作、为什么这样写、该放在哪里
理解wefi-discuss设计选型、需求评估、方案评审
开发wefi-feature新增、修改、重构、优化。quick 和 plan 两个轨道
开发wefi-bugfix报错、回归、结果不对、线上故障。包括 hotfix
验证wefi-verify门禁、浏览器验证、复核验证手册
交付wefi-ship提交、push、开 PR、处理评论和 CI、回写 issue
交付wefi-review-pr审查别人的 PR 或 diff
改进wefi-learn把教训落地，回顾对话
接入wefi-onboard补全项目知识库，选择项目管理系统

SKILL.md 本身很短，10 个加起来 469 行。具体步骤放在各自的 references/ 里， Skill 用到才读。这样常驻上下文的只有路由卡，流程细节不占地方。

回执：AI 开工前先说一句它怎么判断的

在 Codex 和 Cursor 里，AI 读完 Skill 后的第一段话固定是这个格式，说完才动手：

# 不用等确认，说完就继续
[wefi] 模式=feature 轨道=quick · 原因：单页文案改动，不触及接口
      · 下一步：读入口规范 · 改用：/wefi bugfix quick

判断错了你当场就能纠正。Claude Code 不输出回执，直接开工；你自己用 /wefi feature quick 指定时也不输出，因为不会错。

08 · 技术拆解

上下文装载：按需，且不重复

很多 Agent 框架会把文档一股脑塞给模型。这里反过来： 流程文件写明哪一步读什么，没写就不读。

动作 1

装规则

改代码或审查代码之前执行。运行 wefi rules <要改的文件>，读输出中列出的规则文件。

已读过的，本任务不再读
动作 2

装知识

读知识表 .wefi/knowledge/README.md，只读「什么时候读」条件成立的文件。

条件都不成立时不读
动作 3

装业务知识

先搜再看索引。用 wefi domain search 按需求里的页面名、字段名定位章节。

搜不到时才看总入口

8.1为什么先搜再读

有一次需求评估，光读索引就烧掉 3.5 万字符，占整个读业务知识的一半， 结果真正有用的章节还是搜出来的。所以流程改了：先拿需求里的专有名词搜，列出的文件少就直接读， 搜不到才回去看总入口。

这条写在 references/context-loading.md，不是建议，是硬约束。多读进来的东西 会把当前任务真正需要的挤出去。

8.2规则和知识为什么分开放

规则知识
回答的问题必须怎么做现在是什么样
措辞「必须」「不得」「可以」陈述句，不写「必须」
什么时候读改代码、审查代码前写方案、讲解、评估需求时
来源团队 + 项目项目 + 共用业务知识

09 · 技术拆解

更新分发：一个 tag 服务所有人

一套框架服务多个团队，但业务仓库里不提交它的副本。每个人本地有个 clone， 每天第一次用时自己切到最新的 tag。

发布与更新
# 维护人 Actions → release → patch   ├─ 构建并测试   ├─ 提交版本号   ├─ 在后面做一个只含运行文件的提交   └─ 打 tag v0.2.8，推送 # 每个开发者，第二天第一次使用 SessionStart Hook，或 wefi status   ├─ git fetch   ├─ 切到最新的 tag   └─ AI 在回复中说一行「WeFi 已更新到 0.2.8：…」

9.1不更新的情况

  • clone 里有没提交的改动。
  • clone 停在贡献分支上。
  • 设了 WEFI_HARNESS_NO_UPDATE=1。

9.2为什么 tag 只含运行文件

bin/、scripts/、test/、evals/ 是开发用的， 不进发布 tag。业务仓库里的 .wefi/harness/ 因此是干净的。要改框架时， wefi contribute 会从 main 开分支，拿到完整源码。

副作用是：合进 main 的改动不会立刻影响任何人，发版了才到大家手上。 维护人可以攒几个 PR 一起发。

10 · 技术拆解

设计取舍

这五条是刻意选的。写下来，是想改的人能知道代价在哪。

10.1为什么是两档轨道，不是三档

早期是 S/M/L 三档，用下来收敛成 quick 和 plan，hotfix 归到 bugfix 里。 档位每多一档，AI 和人就要多判断一次。两档的边界够清楚： 动一个文件是 quick，碰接口是 plan。

10.2为什么审查阈值是 300 行或共享路径

审查要花真金白银的时间和 token。小改动也派审查，成本比收益高；完全不设阈值， 大改动就裸奔了。300 行是试出来的经验值，写在 .wefi/config.yaml 的 review.max_lines，项目可以自己调。

10.3为什么规则按文件匹配，不按目录

前端的 *.tsx 和 *.css 适用的规则不一样。按目录匹配会读进来一堆没用的， 按 glob 匹配能让只改样式的人不看到 TypeScript 规则。

规则文件的 frontmatter 里写 paths，留空 [] 就是全局生效。 项目规则和团队规则同名时，项目的那份生效。

10.4为什么不做自己的 CI

门禁跑的是项目自己的 typecheck、lint、test、build。 这里不替代 CI，加的是提交之前先跑一遍同样的检查，再把结果写进汇报。

调宽检测是 WeFi 自己加的一项：新写了 any、@ts-ignore、 eslint-disable，或者跳过了测试，都会列出来。

10.5为什么审查交给子 Agent

写代码的那个上下文不能自己批准自己。子 Agent 不继承当前对话，只拿到 diff 和审查清单， 看不到写代码的人当时「我是这么想的」，只能对着代码本身判。

评测：在真实会话里跑

流程写得对不对，读文档看不出来。评测直接用无头模式跑真实的 Claude Code 和 Codex， 在业务仓库副本上发请求，再按断言判。

步骤 1

准备夹具

复制业务仓库，删除 git 远端，运行 sync，提交。

只读，每次运行复制新的
步骤 2

运行场景

evals/run.mjs 发出请求，记录读过的文件、运行的命令、改动和 diff。

支持 --only、--tools、--repeat、--jobs
步骤 3

有无对比

同一请求在有 WeFi 和没有 WeFi 的夹具上各跑一次，按 base 场景的断言判定验收。

现有对照：小改动、接口变更、缺陷修复

断言能查的东西比想象中多：加载了哪个 Skill、读了哪些文件、跑了哪些命令、 diff 里有没有某段文字、改动的文件路径对不对、worktree 的分支对不对。 发版前必须跑路由评测；改了某个 Skill 的流程，还得跑那个 Skill 的端到端评测。
