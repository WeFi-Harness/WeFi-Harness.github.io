01 · 为什么需要

AI 改代码的三个失败模式

直接把需求交给 AI，它并不缺写代码的能力，缺的是「这次该做到哪一步」的判断。 WeFi-harness 把这个判断写进流程，不靠 AI 每次临场发挥。

失败模式 A

改到不该改的地方

加一个按钮，顺手重构了半个模块。或者该写方案的大改动，直接上手改了。

对策：两档轨道 + 300 行审查阈值
失败模式 B

改完不验证就说好了

「已完成」只是措辞。类型没过、测试没跑、页面根本没打开过。

对策：门禁 + 浏览器验证存证
失败模式 C

文档写完就烂尾

方案写了一半，评审记录没留，接手的人不知道当初为什么这么定。

对策：变更目录 + 教训台账

不替代现有工具

WeFi-harness 不做代码生成，也不做 CI。它是一层流程：决定 AI 该读什么、 做到哪一步停下、改完拿什么证明。门禁调用的仍是项目自己的 npm run build、 tsc、eslint。

02 · 安装接入

接入一个业务仓库

接入由一个人做一次。之后每个开发者 clone 仓库，在工具里打开就能用。 框架每天自动更新到最新发布版本。

路径 A

新接入

在业务仓库根目录运行 onboard，克隆框架、生成引导脚本和入口。

npx … onboard
路径 B

0.2 以前接入

已经提交了 .wefi/harness/ 副本、有 wefi-sync.yml 的仓库，运行一次 migrate。

npx … migrate
路径 C

模板仓库

从团队模板仓库创建的新项目，模板中已经包含这些文件，不用再接入。

无需命令

2.1一个人做一次

# 在业务仓库根目录

它把框架仓库克隆到 .wefi/harness/，检出最新的发布版本，并加入 .gitignore。 同时生成引导脚本 .wefi/bootstrap.mjs、各工具的入口和项目知识库初稿。

03 · 工作方式

一次请求走完的步骤

以 issue PDB-901 为例：把文件模板页空列表的文案改成 No file templates yet. Upload one to get started.

你与 AI 的对话
做一下 PDB-901 读 issue PDB-901，写快照 .wefi/state/issues/PDB-901.md。 轨道：quick。单页面文案改动，不触及接口。 新建分支 feat/PDB-901-file-template-empty-text。 装载规则：ui-text.md「空状态必须写明为什么空，并给出下一步操作」。 修改 src/views/system/fileTemplate/index.vue:336。 wefi gate：typecheck、lint 通过。 浏览器验证：空列表显示新文案，控制台没有新增错误。截图已保存。 已完成。待确认：页面没有 Upload 入口，新文案引导的操作在本页不可达。 提个 PR 提交 feat: guide users to upload when file template list is empty，页脚 Refs: PDB-901。 PR #42 已创建。 PDB-901 已评论 PR 链接和验证结论，状态从 New 改为 Pending Review。
  1. 理解请求wefi-feature

    读 issue，写快照，确认要改什么、不碰什么。

  2. 选轨道quick / plan / hotfix

    单页文案改动，不触及接口，走 quick，直接改代码。

  3. 装载规则wefi rules

    按要改的文件挑出适用规则，只读这部分。

  4. 改代码quick

    一个文件，一行文案。

  5. 门禁wefi gate

    类型检查、Lint、相关测试。按改动自动选择检查范围。

  6. 浏览器验证运行验证

    打开受影响的页面，走一遍场景，截图存证。

  7. 审查子 Agent

    quick 轨道在 diff 超过 300 行或改到共享路径时才派。

  8. 交付wefi-ship

    提交、push、开 PR，回写 issue 状态。

什么时候走 plan 轨道

触及接口契约、改动全局架构、跨 3 个以上业务模块时，先写方案。方案经过评审、确认接口契约后， 再分阶段开发，每个阶段结束时派子 Agent 评审。你也可以直接说「走方案」或「直接改」。

04 · 核心概念

六个词就够了

WeFi-harness 的规则文件很多，但需要记住的只有六个概念。其余都是它们的具体化。

模式
请求的类型：feature、bugfix、ship、review、explain、discuss。决定加载哪个 Skill。
轨道
流程的做法：quick 直接改，plan 先写方案，hotfix 只修故障。只用于 feature 和 bugfix。
变更
一件事的记录目录 .wefi/changes/<id>/，含评估、方案、评审记录。
门禁
wefi gate 执行的检查：类型检查、Lint、测试、构建、调宽检测。
项目知识库
.wefi/ 中本项目自己的内容：规则、模块说明、验证手册。
业务知识
.wefi/domain/ 中从 FSD 和接口表生成的共用知识，几个仓库共用。

4.1项目知识库里的文件

路径内容
config.yaml技术栈、门禁命令、审查阈值、项目管理系统、worktree
rules/项目规则。和团队规则一起，由 wefi rules 按文件匹配
knowledge/架构说明和模块说明。README.md 是知识表：哪些改动读哪个文件
verify.md运行验证手册：启动、登录、功能地图、构造数据、已知的坑
lessons.md教训台账
specs/、changes/、decisions/、sources/规格；一件事从评估到完成的文档；设计决策；原始材料索引
state/本地状态：issue 快照、截图、开发服务器。不提交
domain/业务知识的本地 clone，见 domain.repo。不提交

06 · 工作方式

十个 Skill，一条流水线

Skill 是 AI 的入口：每个 SKILL.md 说明什么时候用它、按什么步骤做。 它们各管一段，按阶段串起来就是完整的开发流程。

阶段Skill作用
入口wefi/wefi 的参数、接着做、hotfix、状态、更新、检查、命令列表
理解wefi-explain现有代码怎么工作、为什么这样写、该放在哪里
理解wefi-discuss设计选型、需求评估、方案评审
开发wefi-feature新增、修改、重构、优化。quick 和 plan 两个轨道
开发wefi-bugfix报错、回归、结果不对、线上故障。包括 hotfix
验证wefi-verify门禁、浏览器验证、复核验证手册
交付wefi-ship提交、push、开 PR、处理评论和 CI、回写 issue
交付wefi-review-pr审查别人的 PR 或 diff
改进wefi-learn把教训落地，回顾对话
接入wefi-onboard补全项目知识库，选择项目管理系统

SKILL.md 本身很短，10 个合计 469 行。具体步骤写在各自的 references/ 里， 由 Skill 按需引用。这样路由卡保持轻量，流程细节不占上下文。

08 · 技术拆解

上下文装载：按需，且不重复

Agent 框架最常见的浪费，是把所有文档一次塞给模型。WeFi-harness 的做法相反： 流程文件写明在哪一步读什么，没写就不读。

动作 1

装规则

改代码或审查代码之前执行。运行 wefi rules <要改的文件>，读输出中列出的规则文件。

已读过的，本任务不再读
动作 2

装知识

读知识表 .wefi/knowledge/README.md，只读「什么时候读」条件成立的文件。

条件都不成立时不读
动作 3

装业务知识

先搜再看索引。用 wefi domain search 按需求里的页面名、字段名定位章节。

搜不到时才看总入口

8.1为什么先搜再读

一次需求评估曾在索引上花了约 3.5 万字符，占读业务知识的一半，而核心章节是靠搜索找到的。 所以流程改成：先用需求里的专有名词搜，列出的文件少时直接读；搜不到时才看总入口和章节索引。

这条规则写在 references/context-loading.md。它不是建议，是必须遵守的约束： 多装的内容会挤掉当前任务需要的信息。

8.2规则和知识为什么分开放

规则知识
回答的问题必须怎么做现在是什么样
措辞「必须」「不得」「可以」陈述句，不写「必须」
什么时候读改代码、审查代码前写方案、讲解、评估需求时
来源团队 + 项目项目 + 共用业务知识

09 · 技术拆解

更新分发：一个 tag 服务所有人

框架同时服务多个团队，但业务仓库里不提交它的副本。每个人本地有一个 clone， 每天第一次使用时自动切到最新 tag。

发布与更新
# 维护人 Actions → release → patch   ├─ 构建并测试   ├─ 提交版本号   ├─ 在后面做一个只含运行文件的提交   └─ 打 tag v0.2.8，推送 # 每个开发者，第二天第一次使用 SessionStart Hook，或 wefi status   ├─ git fetch   ├─ 切到最新的 tag   └─ AI 在回复中说一行「WeFi 已更新到 0.2.8：…」

9.1不更新的情况

  • clone 中有未提交的改动。
  • clone 在贡献分支上。
  • 环境变量 WEFI_HARNESS_NO_UPDATE=1。

9.2为什么 tag 只含运行文件

开发用的 bin/、scripts/、test/、evals/ 不在发布 tag 中。 所以业务仓库里的 .wefi/harness/ 是干净的。需要完整源码时，wefi contribute 从 main 开分支。

这带来一个结果：合入 main 的改动不会立刻影响任何人。发版后才到达所有人。 维护人可以合并多个 PR 再一起发。

10 · 技术拆解

设计取舍

下面五条是刻意的取舍。写出来，是为了让想改它的人知道代价在哪。

10.1为什么是两档轨道，不是三档

早期设计用 S/M/L 三档。实际使用后收敛成 quick 和 plan 两档，hotfix 作为 bugfix 的一种。 原因：档位越多，AI 和人都要多判断一次。两档的边界足够清楚： 改一个文件就是 quick，触及接口就是 plan。

10.2为什么审查阈值是 300 行或共享路径

审查要花真实的时间和 token。小改动派审查，成本高于收益；不设阈值，大改动就会裸奔。 300 行是经验值，写在 .wefi/config.yaml 的 review.max_lines，项目可以调。

10.3为什么规则按文件匹配，不按目录

前端的 *.tsx 和 *.css 适用的规则不同。按目录匹配会让读到的规则变多， 按 glob 匹配可以让只改样式的人不读到 TypeScript 规则。

规则文件的 frontmatter 写 paths，[] 表示全局。项目规则用同名文件覆盖团队规则。

10.4为什么不做自己的 CI

门禁调用的是项目自己的 typecheck、lint、test、build 命令。 WeFi-harness 不替代 CI。它增加的是在提交之前跑到同样的检查，并把结果写进汇报。

调宽检测是 WeFi 自己加的：列出新增的 any、@ts-ignore、 eslint-disable、跳过的测试。

10.5为什么审查交给子 Agent

写代码的上下文不能自己批准自己。子 Agent 不继承当前对话，只拿到 diff 和审查清单， 所以它看不到写代码时的「我是这么想的」，只能看代码本身。

评测：在真实会话里跑

流程写得对不对，不能靠读文档判断。WeFi-harness 的评测用无头模式运行真实的 Claude Code 和 Codex， 在业务仓库副本上执行请求，再按断言判定。

步骤 1

准备夹具

复制业务仓库，删除 git 远端，运行 sync，提交。

只读，每次运行复制新的
步骤 2

运行场景

evals/run.mjs 发出请求，记录读过的文件、运行的命令、改动和 diff。

支持 --only、--tools、--repeat、--jobs
步骤 3

有无对比

同一请求在有 WeFi 和没有 WeFi 的夹具上各跑一次，按 base 场景的断言判定验收。

现有对照：小改动、接口变更、缺陷修复

发版前必须运行路由评测。改了某个 Skill 的流程时，必须运行该 Skill 的端到端评测。

不确定配置对不对运行 node .wefi/harness/wefi.mjs doctor，按输出修复
